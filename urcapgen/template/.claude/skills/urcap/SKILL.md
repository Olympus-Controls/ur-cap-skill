# URCaps from one spec

Every URCap lives in `urcaps/<id>/`. **`urcap.toml` is the source**; `./urcapgen gen` writes
`ps5/` (an OSGi bundle in Java 8 + Swing) and `psx/` (plain-JS web components + workers, no
npm) from it. Both platforms render the same URScript from the same template at runtime, and
`./urcapgen parity` proves they do.

The same instructions in plain markdown, for any assistant: `references/*.md` in this folder.
Read the one for the task before you start:

| Task | Read |
| --- | --- |
| Writing or changing `urcap.toml` | `references/spec.md` |
| Behaviour the spec can't express (custom UI, computed script, extra validation) | `references/hooks.md` |
| Anything PolyScope 5-specific, the daemon on PS5, a PS5 build/CI failure | `references/ps5.md` |
| Anything PolyScope X-specific, the backend container, a PSX e2e failure | `references/psx.md` |
| Writing URScript in a template or hook | `references/urscript.md` |
| CI, the required check, releasing, upgrading urcapgen | `references/ci.md` |

## Where you are, and getting started

**Inside a URCap monorepo** (a `.urcapgen` file here or above): use its `./urcapgen`.

**Otherwise**, get urcapgen from, in order:

1. `urcapgen` on PATH;
2. the copy bundled with this skill, in the `urcapgen/` folder next to this `SKILL.md` (the
   uploaded-zip install): `PYTHONPATH=<this skill's folder> python3 -m urcapgen …`.

Then:

- **In a GitHub-connected session** (Claude Code on the web or the Desktop app's Code tab,
  working in the user's repository): the repository is the monorepo. If it has no
  `.urcapgen` yet, run `urcapgen init .` in its root, keeping the README the user created.
  Then create the URCap, verify, commit and **push**. The repository's CI then builds and
  tests it against every PolyScope release. Tell the user to open the repository's
  **Actions** tab to watch it, and when they're ready to release, tag it (see
  `references/ci.md`). Offer to tag it for them.
- **In a plain chat without GitHub** (no network, no Java): nothing can be built or tested
  for PolyScope 5 here. Write the spec, generate, check scripts with `render`, then zip the
  monorepo and offer it as a download. Explain plainly that the robot files are built by
  GitHub: the user should create a GitHub repository, open it in the Claude app's **Code**
  tab, and ask again there.
- **On a user's own machine** (Claude Code CLI): ask where the monorepo should go, then
  `urcapgen init <dir>` and `git init -b main`. Don't push without being asked.

The people using this skill know their robot and Windows. They usually don't know git,
Python or TOML. Speak in robot terms ("a program node called Grip with a force setting from
20 to 185 N"), not file formats. Never ask them to run commands, and summarise what you
built in a sentence or two.

## The loop

1. **Turn the request into a spec.** Ask for what you can't infer (see *Ask, don't guess*),
   then `./urcapgen new <id> --name "…" --vendor-id … --vendor-name "…" --parts …` (parts:
   `installation,program,toolbar,daemon`) or edit an existing `urcap.toml`.
2. **Generate.** `./urcapgen gen <id>` (prints what it wrote, created, deleted). Fix every
   `urcapgen:` error. The messages say exactly what's wrong.
3. **Check the script.** `./urcapgen render <id> <node> --set key=value` prints a node's
   URScript. Read it like the robot will run it (`references/urscript.md`).
4. **Hooks only if needed.** Edit `<Node>Hooks.java` **and** `<node>.hooks.js` together
   (`references/hooks.md`).
5. **Verify.** `./urcapgen parity <id>` (needs a JDK, or Docker as the fallback) and
   `./urcapgen build <id>` (also Docker for a daemon's backend image). Both must pass
   before you commit. If you can't run them here, say so and rely on CI. Never claim
   they passed.
6. **Commit** `urcap.toml`, the generated `ps5/` + `psx/`, hooks and `daemon/` together.
   `./urcapgen gen --check` in CI fails on a stale generated file.
7. **Release** = bump `urcap.version`, merge, then tag `<id>-v<version>` (`references/ci.md`).

## The one rule about files

- A file whose first line says **`GENERATED by urcapgen`** (and every `contribution.json` /
  `en.json`) is the generator's. **Never edit it.** Change `urcap.toml` and regenerate;
  `gen` overwrites it, and deletes it when the spec stops asking for it.
- Everything else under `urcaps/<id>/` is **yours**: `urcap.toml`, `*Hooks.java`,
  `*.hooks.js`, `daemon/`, any helper class or script you add. `gen` creates hooks and the
  daemon once and never touches them again.
- `tools/urcapgen/`, `.claude/skills/urcap/` and `.github/workflows/urcapgen-*.yml` belong to
  urcapgen. `./urcapgen upgrade` replaces them; fix urcapgen upstream instead of here.

## Ask, don't guess

Ask the user before writing a spec when any of these isn't clear from the request:

- **Vendor identity:** `vendor.id`, `vendor.name`, the Java package. These are permanent: a
  changed id is a different URCap to PolyScope.
- **What the robot must do:** the actual URScript, I/O numbers, units, ranges and defaults.
  Never invent I/O assignments or safety-relevant motion values.
- **Platforms and floors**, if they're not the defaults (PS5 5.4, PSX 10.8).
- **Hardware the daemon talks to:** serial/tool port, network address, protocol.

Don't ask about things the spec fixes for you: file layout, names, packaging, CI.

## Never

- Change a program node's `id` or the `urcap.id` / `vendor.id` of a released URCap. Saved
  programs and installations find nodes by them.
- Remove or retype a released field. Old programs carry its saved value. Add a new field
  (its default fills old nodes) and stop using the old one.
- Put robot-specific secrets or customer IP addresses in a spec default.
- Commit `dist/` or `.urcapgen-cache/`. UR's API jars must never be committed or
  redistributed.
- Make the PS5 and PSX hooks write different URScript. Parity exists to catch that.

## Commands

| | |
| --- | --- |
| `./urcapgen new ID --name N --vendor-id V --vendor-name VN [--parts …]` | new `urcaps/ID/urcap.toml` + generate |
| `./urcapgen gen [ID…] [--check]` | regenerate (all by default); `--check` writes nothing, exit 1 if stale |
| `./urcapgen validate [ID…]` / `list` | load specs / list URCaps |
| `./urcapgen render ID NODE [--set k=v] [--after]` | a node's URScript (reference renderer, hooks not applied) |
| `./urcapgen parity [ID…] [--no-java]` | PS5 Java vs PSX JS vs reference, many value cases |
| `./urcapgen build [ID…] [--platform ps5\|psx]` | `dist/`: `.urcap` + `urmagic_<id>.sh` + `.urcapx` |
| `./urcapgen check ID --ps5 5.x` | the built jar against that PolyScope 5's API |
| `./urcapgen e2e-ps5 ID --version 5.x` / `e2e-psx ID --version 10.x` | the URCap in a simulator (Docker; PSX also Playwright) |
| `./urcapgen install ID --ps5-container C` / `--psx-host H [--port 80] [--replace]` | into a sim or robot |
| `./urcapgen sdk [--image 5.x]` | fetch PS5 API jars (automatic on build) |
| `./urcapgen upgrade` | refresh vendored tooling, skill, workflows |
